# Правила работы с кодом


## Пакеты 

- Имена пакетов пишутся в нижнем регистре
- Структура пакетов отражает архитектуру приложения, например: 
  - 'controller' - REST-контроллеры
  - 'service' - бизнес логика 
  - 'repository' - доступ к данным 
  - 'delegateApi' - интерфейсы API 
  - 'dto' - DTO
  - 'entity' - Модели данных 
- Не использовать подчёркивания или дефисы, избегать сокращения без необходимости.


## Классы

- Имена классов и интерфейсов - PascalCase
- Классы, реализующие бизнес-логику, должны иметь понятные имена, отражающие суть (например, `InternshipService`, `UserRepository`).
- Исключения называют с суффиксом 'Exception' ('EntityNotFoundException).
- DTO наименование присваиваем в едином стиле. Сущность User, то Модели данных например: UserCreateDto, UserUpdateDTo, UserViewDto.


## Методы и переменные 

- Имена методов и переменных — camelCase, начиная с маленькой буквы.
- Методы должны быть глаголами или глагольными фразами, чётко отражающими действие или операцию, которую метод выполняет, например:
  - `getInternshipById()` — получить данные,
  - `findUserByEmail()` — найти сущность по критерию,
  - `createInternship()` — создать новую сущность,
  - `updateInternship()` — обновить существующую сущность,
  - `deleteUser()` — удалить сущность,
  - `isActive()`, `hasAccess()` — проверка условия, возвращают boolean.
- Переменные — существительные, отражающие содержимое, например: `internshipDto`, `userId`, `count`
- Константы объявляются с `static final` и именуются в UPPER_SNAKE_CASE, например: `public static final int MAX_INTERN_COUNT = 100;`.
- Алгоритм метода должен соответствовать названию 'getUserOrThrow'


## Правила именования методов мапперов

- Имена методов должны быть простыми и отражать направление преобразования данных.
- Используем глаголы `to` + целевой тип, например:
  - `toEntity` — из DTO в Entity.
  - `toViewDto` — из Entity в DTO для отображения.
- Методы обновления сущности из DTO называют `update`.


# Правила написания методов репозитория JPA, общие принципы (Для корректного SQL запроса, по имени метода)

- Метод должен быть **назван согласно своей функции** и отражать суть запроса.
- Используем соглашения Spring Data JPA:
  - `findBy` — найти по условию
  - `getBy` — получить по условию (синоним findBy)
  - `existsBy` — проверить наличие
  - `countBy` — посчитать количество
  - `deleteBy` — удалить по условию
- После префикса указываются имена полей и ключевые слова (`And`, `Or`, `Between`, `LessThan`, `Like` и т.д.) в camelCase:

  Например:
  - `findByStatusAndRole(String status, String role)`
  - `existsByEmail(String email)`
  - `countByCreatedAtBetween(LocalDate start, LocalDate end)`

- Если запрос сложный или метод становится слишком длинным (>3-4 условий), рекомендуется использовать аннотацию `@Query` с JPQL.


# Основные правила код-стайла

## 1. Форматирование и отступы

- Максимальная длина строки — 120 символов.
- Открывающая фигурная скобка `{` ставится на той же строке, что и объявление класса, метода или конструкции.
- Между методами — ровно одна пустая строка.


## 2. Структура классов и методов

- Порядок в классе:
- 1. Поля
  2. Константы (static final)
  3. Конструкторы
  4. Публичные методы
  5. Приватные методы

## Структура методов

- Методы должны быть короткими — рекомендуется до 15 строк.
- Уровень абстракции кода в методе не должен сильно различаться

## 3. Исключения и обработка ошибок

- Не подавлять исключения без причины. (Не использовать '@SneakyThrows')
- Использовать глобальный обработчик 'GlobalExceptionHandler'

## 4. Логирование

- Использовать логирование '@Slf4j' вместо `System.out.println`.
- Логи должны быть информативными, но без излишней детализации.
- Использовать шаблон с параметрами вместо сложения строк через '+'

## 5. Импорты

- Импорты не должны содержать wildcard (`*`).
- Импорты должны быть отсортированы и сгруппированы (стандартные, сторонние, внутренние).
- Неиспользуемые импорты должны отсутствовать

## Правила написания JavaDoc

- JavaDoc обязателен для:
  - всех публичных классов и интерфейсов;
  - всех публичных и защищённых (`protected`) методов;
  - всех публичных конструкторов;
  - всех нестандартных или сложных публичных полей.

- JavaDoc должен быть информативным, кратким и понятным.

- Структура JavaDoc для методов:
  - Краткое описание назначения метода (что делает).
  - Описание параметров (`@param`) с пояснением, что каждый параметр означает.
  - Описание возвращаемого значения (`@return`), если метод что-то возвращает.
  - Описание возможных исключений (`@throws`), если метод бросает исключения.

## Вложенность функций

- Избегайте глубокой вложенности лямбд и анонимных функций, особенно если тело функции занимает несколько строк.
- Сложная логика внутри `.map()`, `.filter()` и других стрим-операций должна быть вынесена в отдельные методы или конструкторы.
- Глубокая вложенность ухудшает читаемость и усложняет поддержку кода.

# Создание объектов внутри стримов

- Для создания объектов с заданными значениями используйте конструкторы с параметрами или статические фабричные методы.
- Не рекомендуется создавать объект через пустой конструктор и затем вызывать сеттеры внутри лямбда-выражений:
  ``` 
  .map(id -> {
      TeamMember member = new TeamMember();
      member.setId(id.longValue());
      return member;
  }) 
  ```
  
- Вместо этого следует использовать конструктор с параметром:
```.map(id -> new TeamMember(id.longValue()))```

Или фабричный метод:
```.map(id -> TeamMember.withId(id.longValue()))```
